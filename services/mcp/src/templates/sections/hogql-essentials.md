### HogQL essentials

These rules cover routine queries. {reference_pointer} Load it before you use document embeddings, SQL variables, HogQL extension functions, or the observability and LLM tables beyond the basics below, and when a query fails with a memory error.

- **Verify data first.** Do not assume that events, properties, tables, or columns exist. Check events and properties with `read-data-schema`, and tables and columns with `system.information_schema` (see the discovery workflow below). If the data does not exist, tell the user instead of running a query that returns nothing.
- **Tables.** PostHog-created entities live in `system.*` tables (`system.insights`, `system.dashboards`, `system.cohorts`, `system.feature_flags`, `system.experiments`, `system.surveys`, `system.actions`, `system.notebooks`, and more). Filter them with `NOT deleted`. Captured data lives in `events`, `persons`, `groups`, `sessions`, and data warehouse tables. All tables are scoped to the current project.
- **Time ranges.** Every query and subquery on `events` needs a `WHERE` predicate on `timestamp`, including point lookups by session id, trace id, distinct_id, or property value. A time condition only inside an aggregate, like `countIf(event = 'x' AND timestamp > now() - INTERVAL 1 DAY)`, filters nothing. If the user gives no range, pick a day, week, or month to suit the data volume.
- **Properties.** Use `properties.foo.bar`, or `properties.foo['bar-baz']` for keys with special characters. Person properties are `person.properties.foo` on `events` and `properties.foo` on `persons`. Select only the keys you need, never the whole `properties` object.
- **Unique users.** Count `person_id` on `events` (`uniq(person_id)` or `count(DISTINCT person_id)`), never `distinct_id`: one person has many distinct_ids.
- **Joins.** ClickHouse holds the right side of a join in memory. Do not raw-join `events` to itself. Use `IN (SELECT ...)` subqueries, conditional aggregates (`countIf`, `sumIf`, `uniqIf`, `argMax`), or window functions over one scan. Filter and pre-aggregate a subquery before you join it, and use `LEFT ANY JOIN` when each row needs one match. CTEs are inlined, so a CTE referenced twice runs twice. `JOIN ... ON` rejects `>`, `<`, `>=`, and `<=`: use `CROSS JOIN ... WHERE` for those conditions. `WHERE` comes after all joins. When you join system data, keep `system.insights` on the left.
- **Replaced functions.** Use `toFloat()`, not `toFloat64()` or `toFloat64OrNull()`. Use `toDate(x)`, not `toDateOrNull(x)`. Use `lagInFrame()` and `leadInFrame()` with `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`, not `LAG()` and `LEAD()`. Use `count()`, not `count(*)`. Use `bitmapCardinality()`, not `cardinality()`. Use `splitByChar()` or `splitByString()`, not `split()`.
- **Syntax.** Give every expression an explicit `AS` with a descriptive alias. Some short names, such as `fn`, are reserved even after `AS`. Do not end a query with a semicolon. Use `toStartOfWeek(timestamp, 1)` for weeks that start on Monday. Handle nulls before array functions: `splitByChar(',', coalesce(field, ''))`.
- **Text search.** `LIKE '%term%'`, `ILIKE`, and `position()` read the column for every row in the time range. Look for exact values with `read-data-schema` (`event_property_values`) first. If you still need a substring match, filter on `event` and keep the window tight. Pass string constants to `hasToken*` functions.
- **Result size.** Results return 100 rows by default and up to 500 with `LIMIT`. Paginate with `LIMIT` and `OFFSET`. `LIMIT` does not bound memory: avoid `GROUP BY` on unbounded high-cardinality values (raw URLs, ids, free text) over wide windows. Write large JSON results to a file and process them there.
- **Observability and LLM tables.** Heavy LLM fields (`$ai_input`, `$ai_output`, `$ai_output_choices`, `$ai_input_state`, `$ai_output_state`, `$ai_tools`) are not on `events.properties`. Read them from `posthog.ai_events` (columns `input`, `output`, `output_choices`, `input_state`, `output_state`, `tools`) and filter on `trace_id`, not on `timestamp`. `logs` is a root table, but `trace_spans` and `metrics` need the prefix: `posthog.trace_spans`, `posthog.metrics`. Their `trace_id` values are base64, so join them with direct equality. Give every query on these tables a tight `timestamp` window, starting with the last hour. Before you sum a `posthog.metrics` counter, check `aggregation_temporality`: `SUM(value)` is correct only for `delta`. Prefer `query-llm-trace`, `query-logs`, `query-apm-spans`, and `query-metrics` when they fit.
