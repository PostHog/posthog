### Specificity judge impact

| Effect              | 4-5 run 1 | 4-5 run 2 | 5 run 1 | 5 run 2 |
| ------------------- | --------- | --------- | ------- | ------- |
| prevented overgroup | 9         | 10        | 3       | 5       |
| caused undergroup   | 4         | 4         | 4       | 6       |
| net correct         | +5        | +6        | -1      | -1      |

On sonnet-4-5 the judge is worth 5 to 6 extra correct matches per run.
On sonnet-5 it costs one: there is little overgrouping left to prevent, and it still splits 4 to 6 groups that belonged together.
That is why sonnet-5's better matcher does not show up in the post-judge numbers.
Retuning or gating the judge is the lever that would turn the matcher gain into a grouping gain.

### Query generation still retries on 70% of signals

Sonnet-5 returns 4 or 5 queries where `QueryGenerationResponse` caps at 3, in both runs and regardless of the prompt's "1-3 queries" instruction.
Pydantic rejects the response, `call_llm` resends the conversation with the error appended, and the second attempt complies.
That is 58 to 61 extra calls per run, about $0.12 at list price, and the affected signals spend a median 10.7 s in query generation instead of 4.5 s.
Quality is unaffected because the retry always recovers.
Widening the schema and slicing to three, or tightening the prompt, removes the whole cost.

### The report safety judge no longer thinks

With `thinking: adaptive` at `effort: high`, sonnet-5 spends 782 output tokens across 46 judge calls, about 17 per call, against 20,000 to 21,000 for sonnet-4-5's fixed 8192-token budget.
The judge is 3.3x cheaper and its p50 drops from 10 s to 1.5 s, and it still classifies every report correctly on these fixtures.
The fixtures only contain obvious prompt injection, so the judge's behavior on subtle cases is not covered here.

### Latency tail

p50 favors sonnet-5 at every stage except query generation, where the retry dominates.
p95 is not a model property in these runs: the eval fires about 250 calls in its first minute from a single development API key, and the slow calls (36 of sonnet-5 run 1's 47 calls over 10 s) are tiny requests that started in that minute, so they measure rate-limit queuing.
Sonnet-4-5 run 2 shows the same tail (p95 23 s) when it ran in the same window.
On small calls that started after the burst, sonnet-5 is at p50 2.3 s / p95 5.0 s and sonnet-4-5 at 3.4 s / 4.7 s.
Production rate limits for sonnet-5 on the gateway's key are not covered by this eval.

## Method

Run from this branch with `SIGNAL_MATCHING_LLM_MODEL` and `SIGNAL_EMISSION_LLM_MODEL` set to `claude-sonnet-4-5` for the baseline and left at the PR defaults for sonnet-5.
The sonnet-4-5 request shape (assistant prefill, temperature, budget thinking) is byte-identical to master's, so the baseline is master's behavior.

All runs went straight to the Anthropic Messages API rather than through either LLM gateway, so gateway-side behavior (per-team attribution, model allowlists, Bedrock fallback) is not covered.
Tokens, latency, and stop reasons come from a wrapper around the Anthropic client's `messages.create`; the eval's own `$ai_evaluation` metrics were written to disk instead of captured.

Runs went one at a time, in the order 4-5, 5, 5, 4-5.
Signals run concurrently and only the match step is serialized, so lock-acquisition order varies between runs; the two-run spread above is that noise.
