# 2026-08-18

Model comparison: `claude-sonnet-4-5` (current default) against `claude-sonnet-5`, on the same 111 signals from 48 ground-truth groups, same RNG seed, same fixtures.
Both runs produced 45 reports.

Each model drove every LLM stage: pre-emit summarization and actionability, query generation, matching, specificity, report summarization, and both safety judges.

## Aggregate metrics

| --------------------- | ---------- | -------- | ------ |
| ARI                   | 0.733      | 0.802    | +0.069 |
| Homogeneity           | 0.964      | 0.979    | +0.014 |
| Completeness          | 0.930      | 0.936    | +0.006 |
| Mean purity           | 0.972      | 0.981    | +0.009 |

## Match quality

### Pre-specificity (LLM matcher before specificity judge)

| Failure mode | sonnet-4-5 | sonnet-5   |
| ------------ | ---------- | ---------- |
| CORRECT      | 68 (78.2%) | 73 (84.9%) |
| OVERGROUP    | 16         | 6          |
| UNDERGROUP   | 3          | 7          |

On sonnet-4-5 the specificity judge is a net gain, taking 78.2% to 79.3%.
On sonnet-5 it is a net loss, taking 84.9% down to 83.7%: the matcher already avoids most overgrouping, so the judge's remaining effect is to split groups that belonged together.
The judge's thresholds are tuned against a matcher that overgroups, and would want retuning before sonnet-5 ships.

## Cost and latency

| Metric            | sonnet-4-5      | sonnet-5       |
| ----------------- | --------------- | -------------- |
| Wall clock        | 11m 00s         | 11m 49s        |
| LLM calls         | 473             | 510            |
| Input tokens      | 983,119         | 1,265,073      |
| Output tokens     | 55,980          | 55,570         |
| Cost (list price) | $3.79           | $4.63          |
| Latency p50 / p95 | 3652 / 11382 ms | 2781 / 5760 ms |

Cost per stage, as the delta sonnet-5 adds over sonnet-4-5:

| Stage               | Delta cost |
| ------------------- | ---------- |
| match               | +$0.55     |
| query_generation    | +$0.32     |
| safety_filter       | +$0.11     |
| actionability       | +$0.07     |
| specificity         | +$0.05     |
| report_safety_judge | −$0.26     |

Output token counts are flat between the runs, so the whole difference is input.

`match` costs more because each call carries a larger candidate set, which follows from the higher retrieval diversity above.
`report_safety_judge` gets both cheaper and 5x faster (10889ms to 2112ms average) because adaptive thinking spends fewer tokens than the fixed 8192-token budget.

`query_generation` is the one stage whose extra cost buys nothing: 142 calls for 87 signals.
Sonnet-5 returns 5 queries where `QueryGenerationResponse` caps at 3, so pydantic rejects the response and `call_llm` retries with the full conversation resent.
It recovers on the retry, so quality is unaffected, but roughly 55 calls per run are wasted.
Tightening the prompt's query-count instruction should remove about $0.32 of the $0.84 gap.

## Method

Run with `SIGNAL_MATCHING_LLM_MODEL` and `SIGNAL_EMISSION_LLM_MODEL` set per run.

Both runs went straight to the Anthropic Messages API rather than through the internal LLM gateway, so gateway-side behavior (per-team attribution, Bedrock fallback) is not covered here.
Signals run concurrently and only the match step is serialized, so lock-acquisition order varies between runs.
The ARI gain and the pre-specificity overgroup drop (16 to 6) are larger than that noise; the sub-0.01 moves on completeness and recall are not.
Each configuration was run once.
