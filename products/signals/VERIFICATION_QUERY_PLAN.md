# Verification query artefacts

## Goal

Teach Signals report research runs to leave behind a reproducible measurement of the problem they found. After an implementation pull request merges, the report check coordinator can run the same measurement over a comparable window and ask Jev whether the result supports that the fix worked.

The full evidence chain must stay inspectable:

1. Research writes a `verification_query` artefact with the query, baseline result, decision criteria, and MCP provenance.
2. A check binds that artefact to a specific pull request and soak window.
3. The check runs the query over the current window and sends the baseline and current result to Jev.
4. Evaluation writes a `verification_result` artefact that points to both the verification query and the pull request.

## Artefact contract

`verification_query` is an append-only, latest-wins status artefact. The newest valid definition is the report's canonical verification recipe, while older definitions remain in the activity history.

The payload contains:

- A short description of what the query measures.
- An executable HogQL template with allowlisted UTC window placeholders.
- A normalized baseline result with its exact window.
- Success and inconclusive criteria.
- Opportunity evidence, normally returned as a denominator in the same query.
- MCP tool names and documentation references used to construct the query.

Results are bounded and JSON-only. Verification queries should return aggregate evidence rather than raw event or person rows.

## Research behavior

The research protocol must tell the agent to prepare verification evidence while it investigates the report:

- Discover event and property shapes before querying them.
- Use the documented MCP tool schema rather than guessing arguments.
- Prefer a single aggregate query that returns both the symptom and its opportunity denominator.
- Use equal-length windows and explicit UTC bounds.
- Run the exact query before proposing it.
- Never emit a verification query from a failed, truncated, or hypothetical call.
- Fall back to the existing manual verification note for reports that are not meaningfully queryable.

The final structured turn serializes evidence already collected during research. It does not perform new research.

## Trusted snapshots

The model nominates the successful MCP call that produced the query and result. Before persistence, the server re-runs the read-only query with the claimed snapshot bounds and requires the columns and rows to match. An invented, stale, or failed snapshot is dropped.

The pipeline rejects:

- Queries without both window placeholders.
- Queries that cannot be executed as HogQL by the report team's query engine.
- Results over the row or column limits.
- Results whose shape does not match the declared evidence columns.
- Results containing anything other than aggregate numbers, booleans, or nulls.

## Access control

The artefact is generated by the research pipeline and is not writable through the generic artefact API.

The query and result follow the same access policy as report metric queries and snapshots. A viewer without access receives the artefact metadata and decision description, with the query and snapshot values redacted.

Only aggregate numeric, boolean, or null result cells may leave PostHog for Jev. Verification queries must not return identifiers, property values, URLs, names, free text, exception messages, or other row-level data.

## Pull request binding and execution

The research artefact is report-level because it normally predates implementation. When a linked implementation pull request merges, the system creates a `verification_query` report check that references both the source artefact and the pull request.

The check:

1. Starts one hour after merge and runs once an hour for up to 14 days.
2. Runs the stored query over the available post-merge window, capped at the snapshot duration. Jev treats the shorter early windows as inconclusive when they are not yet comparable.
3. Refuses to conclude success when the opportunity evidence is missing or too small.
4. Sends the description, query, baseline result, current result, and decision criteria to Jev.
5. Maps `solved` to `passed`, `not_solved` to `failed`, and `insufficient_evidence` to the retryable inconclusive path.
6. Writes a `verification_result` associated with the exact pull request and source verification artefact.
7. Stops early only when Jev returns a sufficiently confident `solved`; `not_solved`, inconclusive, and provider-error results continue hourly until the 14-day horizon.

When the previous verification result is still the report's newest artefact and belongs to the same query and pull request, the next attempt replaces that row. If another pull request or any other report activity arrived in between, the next attempt appends a new result instead. This keeps a quiet report's work log compact without erasing the boundary created by meaningful intervening work.

Low-confidence model answers are inconclusive. A deterministic metric comparison should continue to use the existing `metric_threshold` check kind instead of Jev.

## Inbox presentation

The report activity log shows:

- `Verification query prepared` with the description and baseline window.
- The HogQL and captured row count.
- The later verification outcome, explanation, confidence, and model.

Restricted query data remains visibly redacted rather than disappearing.

## Test coverage

Extend the nearest existing tests to cover:

- Artefact enum and schema parity.
- Query/result bounds and placeholder validation.
- Research output with a verified query and with the manual fallback.
- Latest-wins re-research behavior and task attribution.
- API write protection and restricted-data redaction.
- Check creation from a merged pull request.
- Jev response parsing, confidence gating, and retryable failures.
- Pull request and verification-query provenance on `verification_result` rows.
- Frontend rendering for complete and redacted artefacts.

Use invented fixtures that cover clear recovery, continued failure, missing opportunity, tiny baselines, schema drift, and fixes whose intended effect is a behavior change rather than complete disappearance. Do not commit production query results from the exploratory dataset.

## Operational controls

The TypeSafe API key, base URL, model, minimum confidence, and egress budgets are environment settings. Requests use the shared egress limiter on the batch lane. Rate-limit and provider failures become retryable errored attempts rather than verdicts.

Research generation and snapshot-validation failures are logged. The latest `verification_result` for each uninterrupted verification period provides the durable Jev outcome, confidence, model, and explanation for later analysis.
