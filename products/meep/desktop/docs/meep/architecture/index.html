Architecture of Meep

A topic gives one responsibility a home: its mission, goals, evidence and an ongoing conversation with one agent. Consider a topic responsible for checkout reliability.

1How a topic works

The system behind a topic

Three processes, three trust domains. The Mac reads and writes only its replica. The server is the single writer for every topic. PostHog does the remote work and reaches Meep only through authenticated endpoints.

Concepts

ConceptWhat it is in the system
TopicOne responsibility, with a mission and goals. One engine worker and one replicated state per topic.
Inbox reportAn evidence-backed finding from a topic agent, a bound workflow or the PostHog Scout feed (§3).
TaskSide work assigned to a person, the topic agent or a separate agent (§6).
RoutineA PostHog workflow bound to the topic, started by a source, schedule, click or engine event (§2).
ContextMission, goals, facts with provenance, rules and passive PostHog references, read into every agent brief.
ViewA script page composed by asking, stored as numbered generations and run in the sandbox (§12).
Needs youThe engine’s cross-topic list of what waits on the person: approvals, questions, failed runs, conflicts, broken connections.

5The approval gate

Any external action, from an agent or a routine, passes one gate. Rules are building blocks too: Allow, Ask, Deny. Starting follow-up work is an action like any other: start-follow-up.

ImplementationPolicyTask transitionsDelivery

6Tasks

A task records side work. The topic agent can assign it to the person, keep it for a later turn, or start a separate agent for independent work.

A sub-agent works in its own PostHog Task. Its result returns as a note to the topic conversation, where the agent can summarize it.
