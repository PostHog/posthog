# Meep MCP architecture and feature plan

Meep uses the PostHog MCP server for work initiated in chat. Django owns private topics, Tasks owns agent execution, Signals owns Scouts and their findings, and Workflows owns deterministic routines. The desktop reads its local replica and opens details on demand.

## Available in a topic

Topic chat and board tasks can call `meep-topic-list`, `meep-topic-get`, `meep-scout-create`, and `meep-scout-set-enabled`. View authoring uses the read tools. People create topics in the desktop app. Tasks supplies the [Meep skill](skills/working-with-meep/SKILL.md) and the MCP server filters the [product catalog](mcp/tools.yaml) by the session credential.

A monitoring request creates a native Signals Scout. Users can pause or resume it in chat. Topic get reads the 50 most recent source-owned reports across the topic's Scouts, subject to the caller's Scout and inbox permissions. The native sidebar shows linked Scouts under Routines and displays cached details offline. Explicit deterministic workflows remain separate.

## Session identity and access

1. Start and resume Meep Tasks with the same stored product profile. Tasks already sends project ID, task ID and origin on initial connection and on follow-up. The consumer currently defaults to `posthog-code` for several products. The MCP catalog requires a task ID matching token introspection and the server-issued `meep_scout:read` scope. Scout writes additionally require `meep_scout:write`. Tasks withholds both grants from other stored profiles, even when a caller supplies Meep origin or task headers. Preserve the scope ceiling on credential renewal. [Sandbox MCP configuration](../tasks/backend/temporal/process_task/utils.py) · [Token introspection](../../posthog/api/oauth/views.py)
2. Apply Meep visibility in the MCP request-state resolver before building the catalog. Use the same exclusions for named tools, CLI search and execution, and scope or feature hints. Apply the credential's scopes, read-only state and tool allowlist as additional limits. Keep ordinary PostHog research tools available. Exclude person-only topic creation from sandbox discovery even when a run can write Scout links. [Request-state resolver](../../services/mcp/src/hono/request-state-resolver.ts)
3. Authorize every operation again in Django. Resolve team, owner and resource from the verified task. Chat and board jobs already map to topics. View jobs need a view-specific binding before gaining topic access. A linked Scout runs with its own Signals credential and emits through the native report channel. Preserve the separation between interactive device APIs and the smaller task API. [Meep topic views](backend/presentation/views.py) · [Topic lookup](backend/service.py) · [Device endpoints](backend/presentation/replica.py)
4. Add a specific write operation and scope when a Meep task needs it. Keep broad replica command submission on the device interface. Pass mutations through the existing domain transitions and atomic command receipts. Include a stable operation key, and preserve domain-specific validation for claimable tasks, stale file writes, view generations and external effects. [Replication](backend/replication.py) · [File service](backend/files.py)

## Scout creation and report delivery

“Keep an eye on signup drop-off” should create a native Scout linked to this topic. “Every Monday, copy these rows to the target table” describes an explicit deterministic routine. A one-off investigation stays in chat. A request that already specifies the investigation and cadence can be acted on directly, with a short acknowledgement. Additional settings belong in details.

Grant the narrowly scoped `meep_scout:write` operation to a bound Meep task. Use the Signals creation service to create the runnable Scout and its skill, preserving skill editor permission, Scout write permission, project access, billing and source access. Persist the binding with the Meep topic. Use a stable idempotency key or explicit Scout identifier for retries. Signals permits different Scouts to share a display name. Under Routines, show each linked Scout with its own icon and its current state. The detail view can expose cadence, instructions, last run, canonical Scout and reports. [Signals tool contracts](../signals/mcp/tools.yaml) · [Canonical project authorization](../signals/backend/facade/scout_access.py)

The Scout skill should collect evidence, check for a prior report, and use the native report channel to emit a new finding or update the earlier one. Reconcile accepted findings against the durable topic link using the Signals report ID. A retry of the same report updates one finding. Keep report evidence, the canonical link, current status and the person's dismissal across repeated deliveries. Subsequent edits to a canonical report must reach the existing topic finding. Ensure a missed notification can be recovered after a worker restart. The topic's ordinary replication path makes reports available to offline devices when they reconnect. Delivery should work while the desktop is closed. [Signals report tools](../signals/mcp/tools.yaml) · [Meep change feed](backend/service.py)

## Delivery order and acceptance checks

1. **Verify identity and skill delivery.** Exercise fresh and resumed chat, board and view runs in both MCP modes. Verify availability of `working-with-meep` inside the actual sandbox. Other Desktop tasks, a generic MCP client, another user's task, and a request with a forged Meep header must receive the expected restricted catalog. Try a hidden tool by name as well as via discovery. The skill build discovers product directories, and the sandbox image installs its built output. Keep Scout-first defaults, approval behavior and tool usage in the shared skill. Reference it from a common Meep task instruction for chat, board work and authoring. Keep view-specific SDK material in the authoring prompt. Release the bundle and sandbox together with the catalog. [Skill source](skills/working-with-meep/SKILL.md) · [Discovery](../posthog_ai/scripts/build_skills/discovery.py) · [Sandbox bundle](../tasks/backend/sandbox/images/Dockerfile.sandbox-base)
2. **Ship a full Scout loop.** From normal chat create a Scout, retry the request, run it, and emit a report. Verify the same linked Scout in the sidebar and the same finding in two replicas, including after a missed event. Test a second Scout with the same display name, a report edit, a denied source, and a cross-project link. Confirm that opening details is optional.
3. **Implement topic operations.** Start with inbox, board, files, sources and facts. Then add policy-aware changes to goals, rules and task state. Test the typed API, MCP invocation, replay, concurrency and the resulting visible desktop state together. A successful terminal tool result must match persisted state.
4. **Complete native workflow and authoring support.** Check explicitly requested deterministic routines against the Workflows permission and activation paths. Exercise a real view-authoring run with an allowed source, a denied source, a stale generation and a malformed script. Verify cancellation and recovery without duplicate execution. For local rendered views, target the PostHog MCP service on port 8787 or the configured override. Django on port 8010 serves the product API.
5. **Validate the product contracts.** Keep tool declarations in the product YAML and regenerate the OpenAPI clients, MCP definitions and CLI catalog with `bin/hogli build:openapi`. Run product, MCP and desktop tests against the same revisions, then start the ordinary PostHog stack and native launcher. Use fresh workspace data throughout.
