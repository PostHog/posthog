List error tracking recommendations for the current project. Each row is a server-computed suggestion with a fixed `type` and a type-specific `meta` payload.

Use this when the user asks how to improve their error tracking setup, what they should fix, or wants to act on their recommendations.

Surface only the few recommendations that matter — don't dump every row. Skip ones that are already done or dismissed.

# Response envelope (every recommendation)

- `type`: one of `alerts`, `rate_limits`, `source_maps`, `long_running_issues`, and the impact lenses `audience_slices`, `quick_leave`, `lost_visitor`, `inflated_counts`, `flow_drop`, `funnel_step`, `suppressed_events`, `support_tickets`, `many_accounts`, `one_account`, `related_issues`, `fires_on_leave`, `known_patterns`.
- `meta`: type-specific payload — see the per-type sections below.
- `completed`: `true` means the recommended action is already satisfied. Nothing to do — skip it.
- `dismissed_at`: set if the user dismissed this recommendation. Skip dismissed ones unless the user explicitly asks.

Only act on recommendations that are not `completed` and not dismissed.

The impact lenses are information, not tasks, so they are always `completed: false`. An empty `meta.issues` means the lens flagged nothing. When a lens sends `meta.evaluable: false`, the project lacks the data it needs, so say that rather than that nothing was flagged. The lenses that rank issues leave out issues that are likely noise; `known_patterns` lists those with the reason.

# Recommendation types

- `alerts` — `meta.alerts` is a list of `{ key, enabled }` for the `issue-created`/`issue-reopened`/`issue-spiking` triggers; `enabled: false` means no alert is wired. To act, use the `authoring-error-tracking-alerts` skill (or the `error-tracking-alerts-create` tool).
- `rate_limits` — `meta.rate_limits` is a list of `{ key, enabled }` for the `project` and `per_issue` ingestion limits; `enabled: false` means it isn't set. To act, check and set them via `error-tracking-settings-get` / `error-tracking-settings-update`.
- `source_maps` — `meta` carries frame-resolution stats (`unresolved_pct` vs `threshold_pct` over a sample); a high unresolved share means stack traces aren't symbolicated. The fix is uploading source maps from the build via the setup wizard:

  ```sh
  npx -y @posthog/wizard@latest upload-source-maps
  ```

  If frames still don't resolve after uploading, use the `diagnosing-stacktrace-symbolication` skill.

- `long_running_issues` — `meta.issues` lists stale active issues (first seen over a week ago, still recurring). To act, use the `triaging-error-issues` skill to work through them, or `investigating-error-issue` to root-cause one.
- `audience_slices` — informational, not an action, and only present for projects in the error tracking impact preview. `meta.issues` lists active issues whose sessions in the last `meta.window_hours` are concentrated in one browser, browser version, operating system, device type, or user-agent class (`bot`, `in_app_browser`, `webview`). Each issue has `slices` of `{ dimension, value, sessions, issue_share, baseline_share, lift }`, where `baseline_share` is that value's share of the project's pageview sessions. A value the pageview traffic barely has gets a `baseline_share` of 2 sessions over the total, so a bot-only issue still shows. Use it to say where to reproduce an issue, for example "95% of its sessions are Firefox, which is 5% of traffic". `meta.evaluable` is `false` with fewer than 100 pageview sessions. It says nothing about how much the issue hurts users.
- `quick_leave` — informational, not an action, and only present for projects in the error tracking impact preview. `meta.issues` lists active issues that fire in the first 3 seconds of a pageview, after which people leave the page within `meta.quick_leave_seconds` seconds at least 1.5 times as often as people with the same browser, device and kind of visitor on the same page without an error. An issue is listed only when this holds on both days in `meta.days` (a week apart, the most recent ending a day ago), and issues that fire as people leave are left out. Each issue has `{ pageviews, quick_leaves, rate, expected_rate, returned_rate, expected_returned_rate }`, where `returned_rate` is the share of the people who left that came back within `meta.return_hours` hours (null without enough data). It usually means the page failed to load properly: describe it as a load failure linked to the error, not as the error driving people away. `meta.evaluable` is `false` when the project sends too little page duration data.
- `lost_visitor` — informational, impact preview only. `meta.issues` lists issues that fire in the first 3 seconds of a pageview, after which the visit ends with no return within `meta.return_hours` hours at least 1.5 times as often as for comparable visitors on the same page without an error, on both days in `meta.days`. Each issue has `{ pageviews, lost, rate, expected_rate }`. It is an association, not proof of cause.
- `inflated_counts` — informational, not an action, and only present for projects in the error tracking impact preview. `meta.issues` lists active issues whose occurrence count comes mostly from a few sessions. Each issue has `{ occurrences, sessions, top_session_share, heavy_session_share, repeating_sessions, timer_sessions, timer_interval_seconds, reasons }`, where `reasons` contains `top_session` (one session produced 20% or more of occurrences), `heavy_sessions` (sessions with 50 or more occurrences produced 30% or more), or `timer` (repeating sessions fire at a regular interval of `timer_interval_seconds`). Use it to say that the occurrence count overstates how many users are affected. `meta.evaluable` is `false` when no issue reached 40 sessions.
- `flow_drop` — informational, impact preview only. Checks up to 8 page-to-page flows found from the last day of pageviews, hour by hour against the same hour on the previous 7 days. `meta.incidents` lists hours from `meta.first_hour` to `meta.last_hour` (24 full hours ending at least 90 minutes ago, so every visit had time to finish) when a flow's success `rate` fell at least 8 points and below three quarters of its `usual_rate`, each with the worst hour's `starts` and `finishes` against `usual_starts` and `usual_finishes`, and `hourly` rates. An incident's `issues` are only those whose visits got the issue on the first page in their first 10 seconds and finished at most half as often as the other visits (`exposed`, `exposed_finish_rate` against `unexposed_finish_rate`), leaving out usually harmless patterns and issues that fire as people leave; most incidents have none. `meta.surges` lists drops explained by extra traffic with the usual number of finishes, which are not breaks. `meta.issues` flattens the attached issues with their flow and hour. `meta.evaluable` is `false` when no flow has enough traffic. Do not describe an issue that merely spiked in the same hour as the cause of a drop.
- `funnel_step` — informational, impact preview only. Links the `flow_drop` flows into chains of 3 or 4 pages people move through in order (`meta.chains`), and checks each hour from `meta.first_hour` to `meta.last_hour` against the same hour on the previous 7 days. `meta.incidents` lists hours when, with at least 200 visits, the share that got through the whole chain fell below 0.7 times its `usual_rate` by at least 4 standard errors. Each incident has `pages`, the worst hour's `starts` and `finishes` against `usual_starts` and `usual_finishes`, `hourly` rates, and `steps` of `{ from_path, to_path, entered, continued, rate, usual_rate, ratio, reached_rate, usual_reached_rate }`, where `ratio` is the step's rate over its usual rate (null with fewer than 30 visits entering the step). `broken_step` is the index in `steps` of the lowest `ratio`, and `clear` is `true` when it is below 0.75 and every other step is at 0.9 or better. A step that fell can be one people retried more after an earlier step failed, so name the step, not a cause. An incident's `issues` come from the `flow_drop` test on the broken step's first page; most incidents have none. `meta.surges` lists drops explained by extra traffic, and `meta.muted` lists chains left out because they dropped more than 3 times in the last 21 days (`incidents`). `meta.issues` flattens the attached issues with the chain's `pages`, `hour`, `broken_step` and that step's `from_path` and `to_path`. `meta.evaluable` is `false` when no chain has enough traffic.
- `suppressed_events` — informational, impact preview only. `meta.issues` lists issues after which people on the page where they fire send up to 3 events much less often than sessions on the same page without the issue: each issue has `path`, `sessions`, `comparison_sessions` and `events` of `{ event, issue_share, comparison_share }`. Issues that fire as people leave are left out. The lens does not know which events matter to the team.
- `support_tickets` — informational, impact preview only, over `meta.window_days` days. `meta.issues` lists issues followed by a support widget ticket in the same session within 5 minutes more often than usual: `{ tickets, sessions, per_1k, ticket_refs }` against `meta.baseline_per_1k` tickets per 1,000 sessions. `meta.evaluable` is `false` without widget tickets that carry a session.
- `many_accounts` — informational, impact preview only, over `meta.window_days` days. `meta.issues` lists issues that reached many accounts (group type 0, named `meta.group_label`): each has `accounts`, `account_share` of `meta.active_accounts` (the accounts seen on pageviews or exceptions in the window), `people` and `sessions`. Use it to say how widespread an issue is across customers. `meta.evaluable` is `false` when no event carries an account.
- `one_account` — informational, impact preview only, over `meta.window_days` days. `meta.issues` lists issues where one account causes most of the sessions: each has `top_account` `{ key, name, session_share }`, `accounts`, `people` and `sessions`. Use it to say an issue is one customer's problem rather than a general one.
- `related_issues` — informational, impact preview only. `meta.issues` lists pairs of issues that fire within 5 seconds of each other in the same sessions: each has `related` (the other issue), `sessions`, `related_sessions`, `both_sessions` (sessions with both at any time), `shared_sessions` (with both within 5 seconds), `leads_share` (of the shared sessions where one came strictly first, how often this one did) and `relation`: `same` (likely the same problem filed twice, a merge candidate), `causes` (this issue comes first in at least 90% of them, and most shared sessions have one strictly first), or `together`. Two issues from one throw land in the same millisecond, which is no evidence either way. `meta.evaluable` is `false` when no issue reached 15 sessions.
- `fires_on_leave` — informational, impact preview only. `meta.issues` lists issues whose first occurrence lands between 1 second before and 2 seconds after a page close far more often than a random moment does (`leave_share` against `baseline_leave_share`), with what the error fires after (`after_navigation_share`, `after_action_share`, `background_share`). Leaving the page likely causes these errors, so they are not evidence of harm, and `quick_leave`, `lost_visitor`, `suppressed_events` and the errors attached to `flow_drop` leave them out.
- `known_patterns` — informational, impact preview only, shown as "Hidden as noise". It reads web exceptions only. `meta.issues` lists loud issues that are likely noise, with `reasons`: `known_pattern` (the most common message matches a pattern that is usually noise: `resize_observer`, `script_error`, `extension`, `chunk_load`, `hydration`, `abort`, `network`, `non_error_rejection`, `environment` for webview bridge and link scanner errors, or `http_status`), `third_party` (in at least half of its events the innermost frame is in a script on another domain that the project's source maps did not resolve), `no_own_code` (in at least half of its events the stack has no frame in the app's own code: no stack, or only dependency frames) or `app_reported` (the app caught it and reported a plain `Error` with a sentence for a message, such as "Not found."). A message shaped like a code bug, such as "Cannot read properties", counts as `code_bug` even when it mentions a noise word. Each issue also has `no_stack_share`, `third_party_share`, `resolved_share`, `own_code_share` and `handled_share`. `meta.classes` splits all error events by pattern and `meta.pattern_events` out of `meta.total_events` is the share that matches a noise pattern. Every other lens leaves these issues out, except `flow_drop` and `funnel_step`, which keep failed loads and requests because a broken deploy shows up as those. So do not describe an issue that appears only here as hurting users.
