# Reviewing ReviewHog

Instructions for the automated reviewer on changes under `products/review_hog/`. Owner: team-devex.

## What failure looks like here

- A review turn that posts the same finding twice, or posts a finding on a head it already published to. Check `published_head_sha` and the dedup inputs.
- A sandbox prompt that lets pull request text pose as instructions: a block after the cache marker, a shell command built from a repository string, or a missing untrusted-content guard.
- A Temporal workflow body change without `workflow.patched(...)`. In-flight reviews replay against the new code.
- An activity that returns a large artefact instead of a report id or head sha.
- Review state read from the wrong head: a follow-up turn must compare against `completed_head_sha`, not the first review.

## Skip

- `eval/` and `adr/`: experiment logs and decisions, not production code.
- `DECISIONS.md` and `ARCHITECTURE.md`: prose, review only when a code change makes them wrong.
- `frontend/generated/`: regenerated by `hogli build:openapi`.

## Evidence and nits

- Anchor every finding to a file and line in the changed code. A guess from a name is not a finding.
- Raise at most two minor findings per review. Prefer none when a must-fix is present.
- Say plainly when nothing needs fixing.
