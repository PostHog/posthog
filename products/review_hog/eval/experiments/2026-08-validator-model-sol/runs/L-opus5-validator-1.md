- **Found:** the mechanical premise holds. `queue_inbox_pr_review` writes no row before `process_inbox_pr_review.delay(...)` (`facade/api.py:149`), the caller logs and swallows the exception (`receivers.py:233-234`), and stamphog registers no sweeper or beat task that could find a missed dispatch.

_perspective: review-hog-blind-spots-general · directly-related: True_

- **Problem:** GitHub can give two close updates the same updated_at value. An inbox fetch for H1 can race a synchronize event for H2. If H2 commits first, the strict greater-than check treats stale H1 as current. The task supersedes the H2 run and creates an H1 run. post_verdict rejects H1 against the live H2 head, so no run reviews H2.

- **Validator:** - **Checked:** The upsert's clock gate (`products/stamphog/backend/tasks/tasks.py:349-362`), the webhook path's equivalent guards (`:1010-1027` and `:1045-1053`), `_supersede_prior_runs` (`:415-432`), the inbox leg's dedupe and recovery (`:1198-1221`), and what a head-mismatched run does at terminal.
- **Found:** The equal-timestamp semantics are pre-existing and deliberate, not introduced here. The webhook path's pre-transaction guard uses strict `incoming_updated_at < stored_updated_at` (`:1023`) with the comment "Equal timestamps proceed (a redelivery of the current head)" (`:1014`), and its locked recheck uses the same strict `>` (`:1045-1049`) followed by the same unconditional `_supersede_prior_runs`. Two racing webhook deliveries with equal timestamps and different heads produce the identical outcome on the existing path. The inbox leg copies that shape, as its own comment states (`:1189`).
- **Found:** The upsert reinforces the same rule. Its conditional UPDATE matches on `payload_updated_at__lte=incoming_updated_at` (`:352`), so an equal-clock payload wins the write on purpose.
- **Found:** Reaching the described state needs a compound coincidence, not just a duplicate timestamp. GitHub must bump the PR twice inside one clock second with the head changing between the two bumps, the inbox fetch must land in that sub-second gap and return the older head, and the newer delivery's transaction must commit before the inbox leg's. Fetch delay alone does not widen this, because the collision depends on GitHub's own update times.
- **Found:** The outcome is a lost review cycle, not a safety breach. The run created at the old head cannot post: `post_verdict` guards the run head against the live head before any GitHub write, and the workflow already dismissed standing approvals at startup, so no approval survives over unreviewed code.
