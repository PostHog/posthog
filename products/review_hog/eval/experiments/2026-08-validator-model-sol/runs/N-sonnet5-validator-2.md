### [✅ VALID] must_fix · security — products/review_hog/backend/api/settings.py:27-32,98-104

**Authorize settings against the canonical team**  
_perspective: review-hog-perspective-contracts-security · directly-related: True_

- **Problem:** The endpoint authorizes membership for the team in the URL. It then resolves a child environment to its parent and stores this setting on the parent. A user with child access but no parent access can enable a parent-owned GitHub approval setting. StamphogCanonicalTeamAccessPermission documents this same authorization boundary for Stamphog endpoints.
- **Suggestion:** Add a canonical-team permission to ReviewUserSettingsViewSet. Check parent membership and token-scoped teams before GET or PATCH. Match the checks in StamphogCanonicalTeamAccessPermission.
- **Validator:** - **Checked:** `ReviewUserSettingsViewSet` (products/review_hog/backend/api/settings.py:84-143), its default permission stack from `TeamAndOrgViewSetMixin.get_permissions` (posthog/api/routing.py:279-304), `TeamMemberAccessPermission.has_permission` (posthog/permissions.py:219-238), and the analogous fix `StamphogCanonicalTeamAccessPermission` (products/stamphog/backend/presentation/views.py:107-143).
- **Found:** `TeamMemberAccessPermission` authorizes only `view.user_permissions.current_team.effective_membership_level`, i.e. membership of the raw URL team (`self.team`), never the parent. `_get_or_create` (settings.py:98-105) explicitly calls `resolve_effective_team_id(self.team_id)` and reads/writes `ReviewUserSettings` under that canonical (parent) team id. `ReviewUserSettingsViewSet` adds no extra permission class, unlike `StamphogCanonicalTeamAccessPermission`, which was built specifically to re-check `effective_membership_level` against `team.parent_team` for this exact class of bug. None of the other review_hog viewsets (reviews.py, perspectives.py, validators.py, blind_spots.py) add a canonical check either, so the gap is systemic to the product, not unique to this file.
- **Found:** the mismatch is genuinely reachable via ordinary session auth, not just tokens. `scope_object = "INTERNAL"` makes `APIScopePermission` allow any session-authenticated user through unconditionally (posthog/permissions.py:570-583) while blocking PAK/OAuth token auth entirely (line 601) — so the exploit path is a logged-in user whose project-level `AccessControl` grant (posthog/user_permissions.py:112-227, keyed strictly by `resource_id == team.id`) covers the child environment but not the parent. This is the identical mechanism `StamphogCanonicalTeamAccessPermission` defends against and is integration-tested in `products/stamphog/backend/tests/test_api.py` (`test_child_scoped_api_key_cannot_reach_parent_rows`).
- **Impact:** such a user can PATCH via the child team's URL and have their own `ReviewUserSettings` row written under the parent team id they cannot otherwise access — an IDOR/tenant-isolation gap. This PR raises the consequence from a comment-only ReviewHog toggle to `stamphog_review_inbox_prs`, which lets Stamphog post a real GitHub approval on the parent-owned, connected repository once an assigned reviewer's row has this flag set, so the newly added field meaningfully increases the blast radius of a pre-existing hole.

### [✅ VALID] must_fix · security — products/stamphog/backend/tasks/tasks.py:169-178,191-196

**The webhook carve-out accepts any bot author**  
_perspective: review-hog-perspective-logic-correctness · directly-related: True_

- **Problem:** \_is_bot_authored accepts every GitHub Bot. During branch fallback, another App can open a repo-native PR from the same task branch. The task lookup then succeeds and marks this PR as self-driving. This bypasses the bot, draft, mode, and permission gates for a PR that Code did not open.
- **Suggestion:** Resolve the expected Code App login from the matched task or configured App slug. Require an exact, case-insensitive login match and Bot type. Return no carve-out when the expected identity is unavailable.
- **Validator:** - **Checked:** `_is_bot_authored` at tasks.py:124-127 — it accepts any user with `type == "Bot"` or `"[bot]"` in the login, with no check against the PostHog Code App's own slug.
- **Checked:** the branch-only match leg in `find_task_run` (products/tasks/backend/webhooks.py:64-78), reached via `find_signal_implementation_run` (products/tasks/backend/facade/api.py:502-506) when `pr_url` does not match. This leg filters only on `branch` and `task__repository__iexact=repository` — no PR-author check, no run-status check, no PR URL check.
- **Found:** `TaskRun.branch` starts as the base branch and is later overwritten by the agent server with the real work branch (documented in products/review_hog/backend/receivers.py:30-31). GitHub deletes a head branch automatically only on merge, not on a plain close, so a rejected or superseded self-driving PR's branch can outlive it in the repo.
- **Found:** `_inbox_rereview_carve_out` (tasks.py:169-178) checks only `_is_bot_authored` (any bot) and that the head repo is not a fork — it never checks that the PR author is specifically the PostHog Code App. So a later, unrelated PR from any other bot-type author, opened on that same lingering branch name in the same repo, matches the old run through `find_signal_implementation_run` purely by branch name.
- **Impact:** A synchronize/reopen/base-retarget event on that unrelated PR then passes the carve-out and skips the bot-author, draft, review-mode, and write-permission gates (tasks.py:867-869, 941-944, 963-969), letting stamphog post a real GitHub approval on a PR PostHog's own agent never opened. This directly undermines the stale-approval trust invariant the product's own CLAUDE.md calls "the big one," and it repeats a bug class the team already closed once elsewhere: `logic/approvals.py`'s sweep requires an exact `<slug>[bot]` login match specifically because "a fuzzy 'any Bot' match must never dismiss or adopt another bot's review" — the same reasoning applies here but is not applied in this carve-out.

### [✅ VALID] should_fix · bug — tools/pr-approval-agent/reviewer.py:698-700

_perspective: review-hog-perspective-logic-correctness · directly-related: True_

- **Problem:** Webhook re-reviews keep `self_driving=True` after the PR changes from draft to ready. This trusted block always says the PR is a draft. A later `synchronize` event on a ready PR therefore gives the reviewer false state.
- **Suggestion:** Pass `pr.draft` to `_format_self_driving`. Add the draft sentence only when `pr.draft` is true. Keep only the stable task provenance for ready re-reviews.
- **Validator:** - **Checked:** `_inbox_rereview_carve_out` in `products/stamphog/backend/tasks/tasks.py:144-215`, which decides whether a webhook delivery re-reviews a self-driving inbox PR, and `_check_prerequisites` / `_format_self_driving` in `tools/pr-approval-agent/review_pr.py:584-607` and `reviewer.py:683-702`.
- **Found:** `_inbox_rereview_carve_out` gates only on the action type (`synchronize`/`reopened`/base retarget) and identity checks (bot author, repo-native branch, opted-in reviewer). It never reads `pr.get("draft")`. Its own docstring at `tasks.py:160-165` states the scope covers later deliveries and that "a ready_for_review flip alone doesn't invalidate the draft-time verdict" — confirming that a `synchronize` event after the PR goes ready still enters this carve-out with `self_driving=True`. `_check_prerequisites` (`review_pr.py:590`) only suppresses the "still in draft" issue when `self.self_driving` is true; it adds no positive statement about the live draft/ready state, and the passing message is just "all clear" (`review_pr.py:607`). - **Impact:** On a real, designed-for code path (new commits land on a self-driving PR after it flipped from draft to ready, while a reviewer is still opted in), the reviewer LLM is told the PR is intentionally still a draft and that draft state carries no signal, when the PR is actually ready to merge. This is the only draft/ready signal the prompt carries, so the LLM has no way to detect the discrepancy. An APPROVE verdict here posts a real GitHub approval (per the PR's Case 1 description), so misleading the model about urgency/finality on a now-ready PR is a genuine correctness defect in a system whose core invariant is that approvals must reflect the code actually reviewed.
- **Priority:** should_fix is appropriate — the underlying gates (bot-author refusal, draft prerequisite) already correctly key off the live `pr.draft` value, so no gate is broken; only the descriptive provenance text fed to the LLM goes stale, which degrades review quality rather than bypassing a hard safety check.

### [✅ VALID] should_fix · bug — products/review_hog/backend/receivers.py:224-234

**Broker failures permanently drop initial Stamphog reviews**  
_perspective: review-hog-perspective-performance-reliability · directly-related: True_

- **Problem:** This post-commit callback catches the Celery publish failure and only logs it. The TaskRun write is already committed, so nothing retries the dispatch. Stamphog rejects the initial bot-authored draft on its normal webhook path. A transient broker outage can therefore skip the only initial review.
- **Suggestion:** Store a pending dispatch before the transaction commits. Retry pending rows from a worker or scheduled reconciler. Keep the consumer idempotent by PR head.
- **Validator:** - **Checked:** `_start_stamphog_review` (products/review_hog/backend/receivers.py:210-234), its caller `handle_task_run_saved` (receivers.py:72-141), `queue_inbox_pr_review` (products/stamphog/backend/facade/api.py), the `process_inbox_pr_review` Celery task, and every code path that can re-touch `TaskRun.output` after the PR leg fires once.
- **Found:** `_start_stamphog_review` wraps `queue_inbox_pr_review(...)` (a bare `process_inbox_pr_review.delay(...)`) in `try/except Exception: logger.exception(...)` with no retry, no persisted pending-dispatch row, and no application-level publish guard. The task's own retry policy (`max_retries=3, default_retry_delay=5`, manual `.retry()` calls) only engages once the task is already executing — it cannot help a broker-down failure at `.delay()` time, since the message is never enqueued.
- **Found:** the webhook backstop that first writes `output.pr_url` (`_record_run_output_field` in products/tasks/backend/webhooks.py) is deliberately idempotent — it writes the field only the first time it is missing and never re-saves once set — and the periodic PR follow-up loop (`products/tasks/backend/temporal/process_task/workflow.py`) only reads `TaskRun.output.pr_url`, it never writes back to it. So after the initial `output` save, nothing re-fires `handle_task_run_saved` with `update_fields` containing `"output"` for that same PR absent a genuine new agent-reported change — there is no scheduled or idempotent re-trigger that would recover from a transient broker outage at the exact moment of dispatch.
- **Found:** per `products/stamphog/CLAUDE.md`'s documented "self-driving inbox carve-out", the receiver leg via `queue_inbox_pr_review` is explicitly the _only_ path for the initial review of a bot-authored draft PR — the webhook leg re-reviews only on synchronize/reopen/base-retarget of a PR that already carries persisted `ReviewRun.output["inbox_review"]` provenance, which is stamped by this same initial dispatch. If the initial dispatch is dropped, the normal bot-author refusal stands and no fallback review path exists for that PR.
- **Impact:** a transient broker outage exactly at this dispatch permanently and silently drops the only Stamphog review for that inbox PR — no data corruption, but a real, will-eventually-occur reliability gap in new code introduced by this PR, matching the reliability-defect bar (swallowed error hides a failure mode). The `should_fix` priority is appropriate: consequence is limited to a missed automated review (not data loss or security), and the trigger window is narrow/rare, so it does not rise to `must_fix`.
