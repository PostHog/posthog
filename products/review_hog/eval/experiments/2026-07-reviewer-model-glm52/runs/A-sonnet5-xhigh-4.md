### [❌ dismissed] should_fix · security — products/stamphog/backend/tasks/tasks.py:113-121

**`_PR_URL_RE` is not anchored to the github.com host, so lookalike domains parse as valid GitHub PR URLs**  
_perspective: review-hog-perspective-contracts-security · directly-related: True_

- **Problem:** `_PR_URL_RE` = re.compile(r"github\.com/([^/\s]+/[^/\s]+)/pull/(\d+)") is used with re.search (unanchored), so it matches "github.com/..." as a substring anywhere in the input rather than requiring it to be the actual host. A string like "https://evilgithub.com/owner/repo/pull/1" or "https://attacker.example/x?u=github.com/owner/repo/pull/1" would still match and yield owner/repo + pr_number, since "evilgithub.com" literally contains the substring "github.com". Given pr_url passed into process_inbox_pr_review can originate from a sandboxed coding agent's own TaskRun output (an untrusted-ish surface per this same product's stated trust model — "PR content is untrusted input everywhere" in products/stamphog/CLAUDE.md), the parser should not be this permissive about what counts as a GitHub URL.
- **Suggestion:** Parse with urllib.parse.urlparse and require parsed.hostname in {"github.com"} (or www.github.com) before applying a path-only regex like r"^/([^/\s]+/[^/\s]+)/pull/(\d+)$" to parsed.path, instead of a single unanchored regex over the whole URL string.
- **Validator:** - **Checked:** The only consumer of `_parse_pr_url` is `process_inbox_pr_review` (the webhook carve-out `_inbox_rereview_carve_out` uses GitHub's own `pr.html_url`, never this parser). Traced how the parsed values flow downstream and what gates them.
- **Found:** `_parse_pr_url` returns only `match.group(1)` (owner/repo) and `int(match.group(2))` (pr_number) — the URL host is discarded and never read again. In `process_inbox_pr_review`, the parsed `repository` is used solely as a lookup key: `StamphogRepoConfig.objects.for_team(team_id).using(write_db).filter(provider="github", repository__iexact=repository, enabled=True, connected_by_user_id__isnull=False).exclude(installation_id="")`. The subsequent GitHub fetch uses the config's canonical name, not the URL: `StamphogGitHubClient(repo_config.installation_id).get_pr(repo_config.repository, pr_number)`.
- **Impact:** The claimed exploit produces no consequence. `https://evilgithub.com/owner/repo/pull/1` and `https://attacker.example/x?u=github.com/owner/repo/pull/1` parse to the identical `(owner/repo, 1)` a canonical github.com URL would — the lookalike host changes nothing about the extracted values. Those values then must positively match a synced+enabled, team-scoped `StamphogRepoConfig`, and the PR is fetched via the team's own App installation against the config's stored repo name. A spoofed host can neither redirect the fetch off github.com nor select an unconfigured repo. Anchoring to `hostname == "github.com"` would close no reachable path. The regex's only real trust-relevant surface — an attacker-chosen `pr_number` within an already-configured repo — is unaffected by host anchoring (a strict `github.com/<configured-repo>/pull/<n>` URL passes it too), so the suggested fix doesn't even address the adjacent concern it gestures at. This is defensive URL-parsing hygiene with no demonstrable failure scenario — a confirmed non-impact, which the precision-over-recall bar drops.

### [❌ dismissed] should_fix · security — tools/pr-approval-agent/review_local.py:316-321

**`bool(context.get("self_driving_review"))` uses loose Python truthiness to gate a security-sensitive bypass**  
_perspective: review-hog-perspective-contracts-security · directly-related: True_

- **Problem:** `Pipeline(0, context.get("repo") or "", self_driving=bool(context.get("self_driving_review")))` coerces the hosted-context field with Python's generic truthiness. Because this flag directly controls whether the bot-author refusal and draft-prerequisite gates are bypassed (see companion findings on review_pr.py/reviewer.py), any non-boolean truthy value would silently enable the carve-out — including a mistakenly-serialized string like `"false"`, `"0"`, or any non-empty string, all of which are truthy in Python despite reading like negatives. The docstring states this key is 'stamped by the server' and expected to default closed, but the code doesn't enforce that the value is actually the JSON boolean `true` rather than any other truthy JSON value (non-empty string, non-empty object/array, non-zero number).
- **Suggestion:** Use a strict identity check instead of bare truthiness, e.g. `self_driving=context.get("self_driving_review") is True`, so only an actual JSON `true` can enable the bypass and any malformed or unexpected value fails closed.
- **Validator:** - **Checked:** The flagged consumer (`tools/pr-approval-agent/review_local.py:321` at PR head, where `Pipeline(..., self_driving=bool(context.get("self_driving_review")))` lives), how `context` is loaded (`review_local.py:396` — `json.loads(Path(args.context).read_text())`), and every producer of the `self_driving_review` context key.
- **Found:** The value is stamped only by trusted server code and is already a real `bool` before it is serialized. `products/stamphog/backend/temporal/activities.py` (`run_review_in_sandbox`) passes `self_driving_review=bool(output.get("inbox_review"))` — explicit `bool()` coercion. `products/stamphog/backend/logic/reviewer.py` `build_reviewer_invocation(..., self_driving_review: bool = False)` types the parameter as `bool` and writes `"self_driving_review": self_driving_review` into the context dict, which is JSON-serialized. JSON round-trips a Python `bool` as `true`/`false`, so `context.get(...)` in the sandbox is always `True`, `False`, or absent (`None` for Action-shaped contexts → `bool(None)` = closed). The integration test asserts exactly this: `context["self_driving_review"] is True`.
- **Impact:** The reviewer's failure trigger — a serialized non-boolean truthy value like `"false"`, `"0"`, or a non-empty string reaching this line — cannot occur given the producer: the flag is coerced with `bool()` and passed through a `bool`-typed parameter before serialization, and the PR author (the untrusted party) controls PR content, not the server-stamped context JSON. `bool(x)` and `x is True` are therefore behaviorally identical for every value that can actually arrive here; the change is pure belt-and-suspenders hardening against a value the upstream types already rule out.
- **Impact:** Per the validation criteria this is a drop: it is a speculative "what if" (depends on an input that can't occur given the call sites and types) and defensive-coding paranoia (guarding against a malformed value upstream coercion already prevents), and the concern is "already handled" at the producer. A real "keep" needs a reachable trigger; this one has none.

### [❌ dismissed] should_fix · best_practice — products/stamphog/backend/facade/api.py:128-155

**queue_inbox_pr_review dispatches the Celery task without transaction.on_commit(), against this repo's own stated convention**  
_perspective: review-hog-perspective-performance-reliability · directly-related: True_

- **Problem:** `process_inbox_pr_review.delay(...)` (line 149) fires immediately rather than being deferred via `transaction.on_commit()`. The docstring states the caller "has already resolved the acting reviewer and checked their ... toggle" right before invoking this facade — the classic shape of a post_save-style listener (per the PR description: "Saving the PR's link onto the task wakes a ReviewHog listener") that typically runs inside the same transaction as the triggering save. If that surrounding transaction later rolls back, the Celery task has already been irrevocably queued and will run against a save that never committed. CLAUDE.md's own architecture guidance explicitly names this exact anti-pattern: "Avoid performing irreversible side effects (... enqueuing Celery tasks) inside an atomic block ... Schedule such side effects after the commit, or use transaction.on_commit() for Celery task dispatch."
- **Suggestion:** Wrap the `.delay()` call in `transaction.on_commit(lambda: process_inbox_pr_review.delay(...))` inside `queue_inbox_pr_review`, so the dispatch only happens once the caller's transaction (if any) actually commits — consistent with how `_start_review_workflow` is scheduled via `transaction.on_commit` elsewhere in this same product.
- **Validator:** - **Checked:** The sole production caller of `queue_inbox_pr_review`, and how it is invoked relative to the triggering `post_save` transaction. Traced the full chain from the `handle_task_run_saved` receiver in `products/review_hog/backend/facade/inbox_hooks.py` down to `.delay()`.
- **Found:** The receiver already defers the whole thing: `if pr_url is not None and settings.stamphog_review_inbox_prs: transaction.on_commit(lambda: _start_stamphog_review(...))`. `_start_stamphog_review` is the ONLY caller of `queue_inbox_pr_review` (which calls `process_inbox_pr_review.delay(...)`), and it is invoked exclusively from inside that `on_commit` callback — there is no other call site. So the Celery dispatch fires only after the TaskRun-save transaction commits (or immediately under autocommit, which `on_commit` handles).
- **Impact:** The finding's premise — that `.delay()` "fires immediately rather than being deferred" and would run against a save that later rolled back — does not hold at the actual invocation. The deferral is correctly placed one level up, at the receiver that actually knows the transaction context; the facade is a generic programmatic entry whose docstring explicitly delegates context to the caller ("the caller has already resolved... and checked their toggle"). Adding a second `on_commit` inside the facade would be redundant defense against a hypothetical future caller that doesn't defer — speculative defensive coding, not a reachable defect. The CLAUDE.md anti-pattern it cites is already satisfied. Drop as already-handled / wrong-premise.

### [✅ VALID] should_fix · bug — products/tasks/backend/facade/api.py:509-511

- **Validator:** - **Checked:** `find_signal_implementation_run` body in the PR diff, the `find_task_run` legs it mirrors (products/tasks/backend/webhooks.py:30-99), the Task soft-delete model (products/tasks/backend/models.py), and whether `run.task` can resolve a deleted row.

Concrete trigger, concrete consequence, touching this product's 'positive identification only' and stale-approval invariants; the fix is a one-line mirror of the filter `find_task_run` already applies on its wizard leg, so it is not overengineering or a speculative edge. Meets the keep bar.
