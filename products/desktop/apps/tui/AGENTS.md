# PostHog TUI (command centre)

An Ink terminal app for PostHog Tasks: a sidebar of your work, tmux-like split panes, and pi chats in the cloud or on this machine.
A chat runs pi, or Claude Code on the user's own Claude plan, here or in the cloud; Codex runs in the cloud on a ChatGPT plan. Other ACP logs are read for display only.

## What it does

- Sidebar: a Today row (its sky glyph follows the greeting's time of day: moon, rising sun, sun, crescent) that opens the day's briefing in the main view (with its composer), split workspaces drawn as trees, each followed by a gap, then an All chats list headed by a New chat row (the main view's new chat while it has one, else it opens one there), that also holds the workspaces' tasks (their row there opens them full width), with run status dots (a cross for a failed run, which no reply brings back), keyboard or mouse selection, and the wheel over it stepping through the chats as the arrow keys do.
- Search: a search over your tasks, each with its sidebar status and when it was last active. Full screen, or from Ctrl+K in an empty pane of a split, drawn in that pane with the pick filling it. A typed query shows the loaded tasks it matches at once (the recent page and open tasks), then the server's answer with any loaded match it left out.
- Panes: tmux-like splits, nested splits, focus by key or click, and a header with where the chat runs, its repo, its PR and its status.
- Cloud chats: transcripts stream from `CloudTaskEngine`, recent history preloads and older pages load on scroll up. The composer starts a run or continues one. A pane shows a new run's first message, the sandbox's setup steps as the backend reports them, and a failure reason. A reply to a stopped run brings the same run back.
- Local chats: pi runs on this machine through the desktop's pi client factory, with a task row on the server and a session file here. Agent dialogs and MCP permission requests are answered on the bottom sheet; a Claude Code question is asked there one question at a time, with every pick sent back as its answers, an option that asks what to do instead has its own text field under it, and the plan it asks approval for shows in the chat as its own text.
- Chat view: tool calls collapse into clickable summaries that highlight under the pointer, web links open on click, a drag selects and copies text, sent images list under their message, a compaction shows as its `/compact` and what it freed, the agent's `show_actions` offers sit on the bottom sheet, and a Claude Code chat whose agent scheduled a wake-up says what it waits on under the chat. A finished turn's line opens with a hedgehog verb picked by the turn's end (`DONE_WORDS` in `runs.ts`: "Foraged for 1m 9s · done 10:09 AM") and, while the run is live, names the background shells the agent left running (pi's harness status, or a Claude Code log's Bash calls with `run_in_background` that no promptless turn has followed: `transcript.shells`), since the agent looks idle until the shell reports back.
- Composer: slash commands with floating suggestions, `!` shell mode, pasted and dropped images, a message sent mid-turn steers the agent, a failed send goes back into the composer, Esc stops the agent and double Esc clears, or on an empty new chat brings back the chat it replaced.
- Notices: a chat's notice sits right-aligned in a row kept above its composer. The composer's top rule shows the agent's background shells, a Claude Code chat's mode, the cost, and the context donut once "Show context in composer" is on in settings.
- Sign-in from inside the app (OAuth, or a local dev login), with the layout saved between runs. A run that starts signed out opens the sign-in sheet by itself, and `/logout` opens it too. A first run shows only a welcome screen (`Welcome.tsx`: the sign-in sheet, no sidebar or chat chrome), then asks who pays, and when the Anthropic plan is picked gets the Claude token on a sheet: it runs `claude setup-token` on the terminal (`claudeSetup.ts`, handed over through `MouseInput.suspend` and Ink's `suspendTerminal`) and reads the token it prints, or takes a paste (`welcome` in `useSend.ts`, `prefs.welcomed`). Settings has the same run row.
- Billing (`/billing`): who pays for new chats, saved between runs. PostHog runs pi on the gateway everywhere. ChatGPT runs pi on the GPT model here, after a browser login kept in pi's `~/.pi/agent/auth.json`, and Codex in the cloud on the account connected to PostHog ("Connect ChatGPT for cloud runs": a second browser login whose tokens go to PostHog, since it rotates them; `codexCloud.ts`). Picking ChatGPT, or starting a chat that lacks the login its place needs, runs that sign-in on a sheet (`signInToChatgpt` in `useSend.ts`); settings has both logins too. Anthropic runs Claude Code in the cloud with a `claude setup-token` token, pasted once in settings (Ctrl+; or `/settings`) and kept in `~/.config/posthog-tui/claude-token`; the TUI hands it to each run's sandbox when asked, so it must be open while a chat starts. A local chat on the Claude plan runs the user's own `claude` binary (the one `claude auth login` signed in) through the desktop app's agent service, so pi's `/model`, `/effort`, `/compact` and the cost donut are off on it; `!` runs the command here instead.

`README.md` is the user-facing guide (install, billing, shortcuts, commands); npm shows it on the package page. Keep its tables in step with `help.ts` and `SLASH_COMMANDS`.

## Run and test

- `pnpm dev` (from this folder) starts the app through Vite, so edits hot-reload into the running screen.
- `pnpm build` bundles the app into `dist/` with esbuild (pi stays a dependency on disk, since it reads its themes beside its own modules), and `pnpm start` runs that build: no Vite, no hot reload, half the startup time. `files` in `package.json` is what npm publishes.
- Install: `npm i -g @posthog/tui` (Node 22.19+; `claude` on PATH for local Claude Code chats), or `posthog-cli code` from the Rust CLI, which runs the latest package through `npx`. A merge to master touching this folder tags `tui-vX.Y.<n>` (`desktop-tui-tag.yml`, patch = commits since the base `tui-vX.Y` tag) and `desktop-tui-release.yml` builds the agent workspace, builds and tests the TUI, smokes the packed tarball in a temp prefix with `posthog-tui --version`, and publishes with provenance. `--version` is answered by the launcher before the app loads.
- Tests: `../../node_modules/.bin/vitest run` or `hogli test products/desktop/apps/tui`. Typecheck: `../../node_modules/.bin/tsc --noEmit -p .`.
- `@posthog/agent` and `@posthog/harness` resolve to their `dist/`. After changing them, rebuild with `pnpm --filter <package> build` (harness types: `pnpm build:types`).

In the app: Ctrl+\\ splits side by side and Ctrl+Shift+\\ (Ctrl+|) stacks, Cmd works in place of Ctrl, and legacy terminals send both as Ctrl+\\; Ctrl+C twice closes a chat, Ctrl+N starts a new chat (in the focused pane inside a split workspace, the main view elsewhere) and Ctrl+Shift+N one in the main view from anywhere, Ctrl+B (or Cmd+B, since tmux keeps Ctrl+B) narrows the sidebar to its logo, saved between runs, Ctrl+K (or Cmd+K) searches tasks and Ctrl+Shift+K searches full screen even from an empty split pane (both Shift forms need the kitty keyboard protocol; a legacy terminal sends them as Ctrl+N and Ctrl+K), ← and → fold and unfold the workspace of the chat the sidebar cursor is on (folded, its title row takes the cursor and keeps the mark; Enter or a click on the title opens it, unfolding it, and a click on an open one folds it), Ctrl+; opens settings, Ctrl+M steps a Claude Code chat's mode and Ctrl+Shift+M steps it back (both need the kitty keyboard protocol, since a legacy terminal sends Ctrl+M as Enter; it wraps), Ctrl+[ and Ctrl+] step back and forward through the chats visited (`history.ts`: each pane focus or chat change is a spot; a legacy terminal sends Ctrl+[ as Esc, so only Ctrl+] works there), Ctrl+R reloads all code, Ctrl+Q quits.
Slash commands: `/model`, `/effort`, `/mode` (Claude Code chats, local or cloud: plan, auto, default...; a new chat on the Claude plan shows the mode it will start in and the pick sets it), `/compact [focus]`, `/new`, `/repo`, `/clear` (local chats), `/rename`, `/rename-workspace`, `/search`, `/settings` (or `/config`), `/help` (every shortcut, full screen, from `help.ts`), `/billing`, `/mcp`, `/local`, `/cloud`, `/login`, `/logout`, plus the live run's own commands. `/rename` and `/rename-workspace` with no name put the current one in the composer to edit.
`/new` and Ctrl+N in a split pane make that pane a new chat. Anywhere else they clear the main view. The pane remembers the chat it showed, and a double Esc on the empty chat brings it back.
`/repo` opens a searchable multi-select of the GitHub repositories the team's and the user's GitHub connections reach (type to search, Space ticks, Enter saves). Each pane keeps its own pick for new cloud chats, saved between runs; a pane that never picked uses the repository of the folder the TUI started in.
`/local` and `/cloud` switch the current pane and set where new chats in other panes run, saved between runs.
`!` in an empty composer enters shell mode (orange `!` prompt and rule; Backspace on an empty command leaves it). Enter runs the command where the chat's agent runs (this machine or the sandbox), then tells the agent what ran and what it printed as a message of its own (`shellMessage`), so it reacts at once; pi's `bash` RPC runs it for a pi chat, the TUI runs it for a Claude Code chat.

## Things that bit us

- **Tests and smoke runs never touch the real `~/.config/posthog-tui`.** `src/testHome.ts` gives each test file its own temp `HOME`, because the files run in parallel and one file's session files once showed up in another's sidebar. Drive the app in a pty with a temp `HOME` too, or a run can overwrite the user's session and layout.
- **Ink draws an empty string with no height.** A blank row must carry a space, as `ChatView.render` does.
- **Flex layout rounds half rows and leaves gaps.** Splits get whole-cell sizes from `splitSizes`, and a split with its own divider sizes its children inside that divider.
- **Ink enters the alternate screen without moving the cursor home.** The full-height root box is what makes it draw from the top.
- **A Vite full reload skips `dispose`.** `main.tsx` also tears down on `vite:beforeFullReload`, and a disposed `MouseInput` no longer switches raw mode, or the old copy turns it off under the new one. Ctrl+R triggers a full reload through `globalThis.__posthogTuiReload`, set in `cli.mjs`.
- **The commit hook runs `biome check --write --unsafe`.** Its exhaustive-deps fix once added a whole task object to a `useEffect` and re-subscribed every 10 seconds. Key effects on ids, or call changing functions through a ref.
- **`MouseInput` sits between the terminal and Ink.** It strips mouse reports and hands raw keys to the app, which splits them with pi's `StdinBuffer`. App keys (`isAppKey`) go to Ink handlers, and everything else goes to the focused composer or an open sheet.
- **pi components pad for a full screen.** `ChatView` trims their blank edges, strips OSC 133 marks, and spaces blocks itself.
- **pi draws no cursor of its own through Ink.** Since pi 1.2 the editor wraps the cursor cell in zero-width `FAKE_CURSOR` markers that pi's own screen resolves at draw time; `Composer.render` turns them into an inverse block on the focused pane (none while a selection is live) and strips them elsewhere. An upgrade that renames the markers loses the cursor silently; the composer test pins it.
- **A dropped file arrives as a paste of its path, with no position.** The terminal reports motion only as the pointer crosses cells, so `paneAtDrop` sends the path to the pane under the last report however old it is, unless a key was typed since (a typed paste stays in the focused pane). Terminals with kitty's OSC 72 drag-and-drop protocol report the drop point itself; the TUI does not use it yet.
- **An agent editing the TUI from inside it reloads the app it runs in, mid-edit.** Every saved file hot-reloads, and a local agent's session lives in that process. Write each step so the app still loads and renders: add a module or export before the code that imports it, and make a callee accept a new argument before its caller passes it (and the reverse when removing). A step that broke this ended the session before `ErrorBoundary` and the `cli.mjs` recovery; now it shows an error screen, and the TUI reloads by itself when the next change loads.
- **The engine stops watching a run once it ends.** A run brought back with `resume_in_cloud` keeps its id, so the store notes a finished run's watch as closed and opens a new one for its next subscriber or hold; a newer copy of the same run in `fresh` wins over the work list (`findTask` compares `updated_at`).
- **The backend fails a cloud run whose pi turn ends with `stopReason: "error"`, and destroys its sandbox.** An Esc can cut off a model request that then reports an error. The agent's translator ends such a turn as cancelled (`translatePiConversation.ts`); a cloud sandbox only gets that fix with a new `@posthog/agent` release.
- **Local agents live in a global map keyed by task id**, so they survive hot reloads. In tests, give each local chat its own task id, or a later test gets an earlier test's agent.
- **The cloud engine lives in a global map keyed by account, for the same reason.** A cloud Claude Code sandbox asks the TUI for the Claude token once and waits 120 seconds; the engine's watcher answers it. A hot reload used to rebuild the engine and every watcher, and a request that landed in that gap was never answered ("The Claude token did not arrive"). `cloudEngineFor` keeps the engine and reads tokens through the latest sign-in. The watch itself followed the panes, so a run opened and then left before its sandbox booted had no watcher when the request came; `PiChats.start` holds the run (through `agentRestarted`) until its agent reports in, and a reply that brings a run back holds it the same way. The hold is taken before the sandbox boots: the sandbox sends the request once as a live frame that is never written to the run's log, so a stream opened after it has nothing to replay. The backend answers `resume_in_cloud` before the run's status leaves its finished state, and the engine drops a watch it opens on a finished run, so the hold opens it again every few seconds until the run is live (`REOPEN_MS`), or the request came to nobody; a failed or cancelled status counts as the restart's own only once the run was live, since the previous life's failure is what a resume is for. Desktop sidesteps this by resuming the run, which makes the sandbox ask again.
- **Every watch of a run used to be its own engine watch, tied to a React effect.** Panes and the turn tracker stop and restart their subscriptions within one render; the engine closes a run's stream at zero watchers and reopens the next at its latest entry, so a reply sent in that gap went unseen, and resuming from a count made the engine replay the stream's leaf and count it as new, so a reply read mid-stream came through doubled. The store now keeps one engine watch per run for as long as anyone holds it, plus a grace period (`UNWATCH_GRACE_MS`) so a stop and restart in one render never closes it, and one view that every subscriber reads, so the sidebar and the pane cannot disagree about a turn. `applyUpdate` still drops entries the view holds by their `event_id`, which only helps once the sandbox's agent stamps them.
- **Local Docker sandboxes need the agent-server bundle linked**, or the pi capability probe fails. See `products/tasks/backend/sandbox/images/Dockerfile.sandbox-local`.

## Open ends

- Before a run exists, `/` lists only the built-in commands. The plan is bundled skills and the repo's `.claude/skills` from disk, then user skills with the desktop's upload step.
- A local chat has a task row but no run, and its conversation lives only in its pi session file on this machine (a local Claude Code session starts with `skipLogPersistence`, or the agent's log writer 404s against the server once a second). The server hears nothing about local activity, so the sidebar sorts local chats by their session file's last change.
- The desktop app keeps its own local pi session files, so a TUI local chat opened there shows no conversation, and the reverse.
- Cloud sandboxes run the published `@posthog/agent`. Harness and agent changes on this branch (background shells, compaction details, the aborted-turn fix) reach cloud chats only after they land on master and the sandbox image picks up the release.
- pi chats have no auto, manual or plan modes: pi has none, and the harness adds none. A Claude Code or Codex chat's modes come from the `mode` option in its ACP log (the session's opening result and each `config_option_update`); a cloud run switches through the `set_config_option` command and starts in the mode `initial_permission_mode` names. The desktop app's embedded chat view shows Claude's mode picker on pi chats, and it does nothing there.
- A cloud sandbox stops when idle, and its background shells stop with it.
- Long cloud pi chats stop taking messages. Before a follow-up, the backend rebinds the sandbox's MCP credentials once its binding marker expires (half the token lifetime), and the pi agent server has no `refresh_session` command, so the backend fails the delivery closed. The TUI shows the failed `followup_delivery` step and puts the message back (`deliveryFailure` in `runs.ts`); the fix is `refresh_session` in the pi agent server.
