# personhog-coordination

Etcd-based coordination primitives for dynamically assigning Kafka partitions to PersonHog writer pods and orchestrating zero-downtime handoffs when pods join or leave.

## Why this crate exists

PersonHog processes person data sharded across Kafka partitions. Each partition must be owned by exactly one writer pod at a time (single-writer invariant). When pods scale up, scale down, or crash, partitions need to move between pods without losing inflight requests.

This crate provides the coordination layer: a coordinator assigns partitions to pods, and when assignments change, it orchestrates a handoff protocol that moves traffic through routers without dropping requests.

## Why etcd

Etcd gives us the building blocks we need without rolling our own consensus:

- **Leases** for failure detection: pod keys auto-delete when a pod crashes, triggering reassignment
- **Watches** for reactivity: components react to state changes instead of polling
- **Transactions (CAS)** for leader election: only one coordinator runs at a time. Standby candidates watch the leader key rather than campaigning on a timer, so election traffic tracks how often leadership changes instead of how many candidates are running
- **Strong consistency**: all participants see the same state

## Components

| Component | Crate | Role |
| --- | --- | --- |
| **Coordinator** | `personhog-coordination` | Leader-elected singleton. Watches pods, computes partition assignments, orchestrates handoffs. |
| **Writer pod** | `personhog-leader` | Owns partitions, processes person data. Registers with etcd, responds to handoff events (warm cache, release partition). |
| **Router** | `personhog-router` | Routes requests to the correct writer pod. Maintains a local routing table from etcd watches. Executes traffic cutover during handoffs. |
| **etcd** | (external) | Source of truth for pod registrations, partition assignments, and handoff state. |

## How it works

### Registration

Each writer pod and router registers in etcd with a lease-backed key. If a pod crashes, the lease expires, the key is deleted, and the coordinator reacts.

### Assignment

When the set of active pods changes, the coordinator computes a new partition-to-pod mapping using a pluggable `AssignmentStrategy` (jump consistent hash or sticky balanced). It diffs the result against current assignments to determine which partitions need to move.

### Handoff

Partitions that need to move go through a four-phase state machine. The protocol is designed so that no acknowledged write is ever lost across a cutover, even though four independent components (coordinator, old owner, new owner, routers) participate.

```text
Freezing --> Draining --> Warming --> Complete --> (deleted)
```

1. **Freezing**: Coordinator creates the handoff, snapshotting the then-registered routers into a membership record the handoff refers to by `freeze_quorum_ref`. Routers begin buffering ("stashing") incoming writes for the partition and write a `RouterFreezeAck`. The old owner does *not* yet drain — it continues serving until the quorum has acked, because while a single router still forwards traffic to the old owner the inflight count cannot meaningfully be observed as zero. The required ackers are the creation-time snapshot intersected with the live registry, so the requirement only ever shrinks: a router that dies drops out, and one that registers later is never added (it anchors its watch after the handoff and its table starts fail-closed, so it cannot be routing to the old owner and its ack is not needed — it writes one anyway as it bootstraps, which is what keeps the pre-membership fallback satisfiable). Once every required router has written an ack matching the current handoff's `handoff_id`, the coordinator advances to `Draining` via a compare-and-swap on the handoff key's `mod_revision`.

2. **Draining**: No router can forward new requests to the old owner anymore (every router is stashing). The old owner waits for its inflight request handlers to complete, then writes a `PodDrainedAck`. Because the leader's produce path awaits the Kafka delivery future before returning success, "no inflight" implies "every write this pod ever acked is durable in Kafka." When the ack arrives (or the old owner is no longer registered), the coordinator advances to `Warming`.

3. **Warming**: Kafka high-water mark for the partition is now stable — no producer can append. The new owner consumes the changelog from the writer's last committed offset up to the current HWM, populating its cache, then writes a `PodWarmedAck`. The coordinator atomically writes both `phase=Complete` and the new `PartitionAssignment` in a single etcd transaction.

4. **Complete**: Routers observe the handoff completion, drain their stashed writes to the new owner, and resume routing through the standard table lookup (which now points at the new owner). The old owner observes Complete and releases its partition cache. The coordinator deletes the handoff and ack keys.

The handoff record carries `old_owner: Option<String>`. `None` denotes an initial assignment with no prior owner — there's nothing to drain, so the protocol short-circuits and skips `Draining` entirely, advancing `Freezing → Warming` once router quorum is met.

Every handoff carries a unique `handoff_id`, and every ack (`RouterFreezeAck`, `PodDrainedAck`, `PodWarmedAck`) echoes it. Quorum checks count only acks whose id matches the current handoff, so a stale ack left over from an earlier handoff of the same partition can never satisfy a later one.

#### Where the freeze quorum's membership lives

Every handoff a plan creates shares one membership — the router registry as the coordinator saw it — so the plan writes it once under `freeze_quorums/{id}` and each handoff carries only that id. Written into each handoff instead, it grew with the fleet, and a plan transaction grew with the fleet times the partition count: at a few hundred of each it passed etcd's `--max-request-bytes`, which rejects the whole transaction, and it was paid again by every list of handoffs. The coordinator's reconcile tick deletes membership records no live handoff refers to, listing the ids before the handoffs so a record written mid-sweep is never a candidate.

Resolution fails closed. An id whose record is missing reads as *unknown* membership, which falls back to requiring every live router — the same rule as a record that predates the field. Both are stricter than any recorded membership, so a lost or prematurely collected record can only delay a handoff. The distinction that matters is against *empty* membership, which requires nobody: that is a real snapshot (zero routers registered at creation), and it must never be what an unresolvable reference degrades to.

Only the coordinator judges the quorum, and only one coordinator leads at a time, which is what makes the roll safe. A new leader reading a record written before this change uses the membership it carries inline. An old leader reading a record written after it sees no membership at all and falls back to requiring every live router — satisfiable, since a router that joins late acks in-progress handoffs as it bootstraps, so a mid-roll failover slows a handoff rather than wedging it.

##### Accepted degradations

Each is bounded by something that already exists, and none of them can advance a handoff early or lose an acked write. Detail lives at the code site.

| What degrades | When it happens | What bounds it |
| --- | --- | --- |
| A handoff loses its membership reference and falls back to requiring every live router | An old-binary leader advances that handoff mid-roll: phase advances rewrite the whole record, and its struct has nowhere to carry the reference through | The roll — a finished one cannot produce it. The fallback is the stricter rule, so it only ever delays a handoff. Not counted: `unresolved_freeze_quorums_total` sees references that fail to resolve, never ones stripped |
| A pod stays registered as `Draining`, and graceful handoffs toward it park until it expires | Both the drain's bounded setup and the bounded revoke time out against a hung etcd | One lease TTL, the same window a pod crashing right after registering already costs |
| A cancelled session leaves a registered phantom — a pod phantom parks writes behind plans toward it, a router phantom stalls freezes created in its window | A session begin is cancelled after its registration may have landed, and the bounded revoke times out too | One lease TTL, as above |

A watcher etcd cancels — compaction, watcher pressure — is delivered as an ordinary response with `canceled` set and nothing ever after it. Every watch loop that must stay live treats that response as a failed attempt (`live_watch_response`), so it surfaces in the same restart-and-rebuild path as a broken stream rather than parking the loop on a dead watcher. Two loops handle it differently: the pod's own-registration watch — best-effort acceleration of a teardown that completes without it — ends for the session instead, and the standby's leader watch waits out its fallback window and re-reads, so a cancelled watch never observes an opening slower than a stalled one and no failure mode costs etcd more than the healthy cadence.

#### Why the Freezing/Draining split matters

If a single phase served both purposes (router stash *and* old-owner drain in parallel), a slow router could send a final write to the old owner *after* the old owner observed inflight=0 momentarily and wrote `DrainedAck`. The coordinator would then advance to Warming based on a stale ack. The old owner would still process that final write, advancing Kafka HWM past the point warming snapshots, and the new owner's cache would be missing the record — silently stale. Sequencing the phases ensures "no inflight" actually means "no producer can append more."

### Recovery

Several failure modes are handled explicitly:

- **Dead `new_owner`**: If the new owner's etcd registration disappears (lease expired, deregistered) before it can ack warming, the planner cancels the handoff **by replacement**, never by naked deletion: it picks a replacement owner and rewrites the record toward it, reaffirms the current owner (`old_owner: None`, phase `Complete`) when the partition should stay put, and only deletes — handoff plus all of its acks in one transaction guarded on the record's `mod_revision` — when nothing is placeable at all. The same machinery serves the second cancellation trigger, a handoff that outstays its phase deadline (`past_phase_deadline`). Either way a concurrent actor loses the CAS cleanly, and routers never observe a gap between owners.
- **Dead `old_owner`**: A dead old owner is deliberately *not* grounds for cleanup. A pod that is no longer registered can't produce writes, so the drain requirement is vacuously satisfied — `check_phase_advance` treats a handoff whose `old_owner` is absent from the registered set as drained and advances it in place toward `Complete`. An `old_owner` that is still registered must write its `DrainedAck` before the handoff advances.
- **Cancellation by replacement**: A handoff record is never deleted while non-terminal. To cancel one — its new owner's registration disappeared, or it outstayed its phase's deadline — the planner atomically *replaces* the record, under its `mod_revision` and with the predecessor's acks deleted in the same transaction, with whatever resolves the routers' stashes: a successor `Freezing` handoff when the plan re-places the partition (stashes ride into it without observing a gap), or a reaffirm — `Complete` toward the live current owner, `old_owner: None` — when the placement stands (stashes drain home through the ordinary Complete path, and the owner pod converges back to serving). Only when neither exists (owner dead, nothing placeable) is the record deleted, which is safe fail-closed. A deletion event therefore has exactly one protocol meaning — cleanup after `Complete` — and routers treat it as inert. The cancellation log and a `freeze_ack_missing_total{router}` counter name the required routers whose acks never arrived, so a freeze wedge attributes itself to the non-participating router.
- **Chunked plan application**: A plan is applied in transactions sized to etcd's `--max-txn-ops` (`ETCD_MAX_TXN_OPS`, default 128); an unchunked over-budget plan would be rejected outright and retried forever. Atomicity is per partition — each unit keeps its guards and writes in one transaction — so a conflicted unit stands down alone and a partially applied plan is placement drift the next replan heals. Stateright explores partial application (`chunked_plans`).
- **Phase-aware deadline**: Time-in-phase is bounded, not total age — wedged is a property of a phase. Freezing and Draining wait only on acknowledgements and share a tight budget (`COORDINATOR_HANDOFF_DEADLINE_SECS`, default 120 s); Warming replays a changelog whose length scales with the partition and gets its own generous budget (`COORDINATOR_WARMING_DEADLINE_SECS`, default 1800 s, 0 disables). A total-age deadline would cancel a legitimately long warm and restart it from zero, forever. The reconcile tick detects both cancellation triggers and wakes the planning loop; the replacement itself is a planning decision.
- **Participant stall watchdog**: A router's registration is lease-backed, and the lease keepalive is its own task — so a router whose handoff watch loop has stalled would stay registered (counted in freeze quorums) while never acking. The watch loop stamps a progress marker from a ticker arm inside its own select; a watchdog task fails the run when the stamp goes stale (`ROUTER_PARTICIPANT_STALL_SECS`, default 60 s), deregistering the router on the way down so quorums stop counting it and the process supervisor restarts a healthy participant. Pods deliberately get no such watchdog: their converge loop legitimately blocks for warm-duration, and a pod that stops acking is routed *around* by the phase deadline and replacement instead of being restarted mid-warm.
- **Level-triggered reconciliation everywhere**: Watches are the latency path; every participant also has a truth path that re-derives its state from a fresh snapshot. The coordinator's tick re-evaluates handoffs; the router's reconcile pass (an arm of its watch loop, `ROUTER_RECONCILE_SECS`, default 5 s) re-asserts stashes and freeze acks, converges its table to the assignment authority, and drains any stash whose partition has no handoff to the assignment owner — which heals a missed Complete, a silently dead watch stream, or an out-of-protocol raw deletion; the pod's tick re-converges every involved partition, including locally-held state the durable world no longer mentions. Every reconcile action is idempotent against the event path. Reconcile failures are tolerated, not fatal: a failed pass leaves the participant exactly as stale as the previous tick (the watch-driven steady state), so brief etcd blips never restart the fleet — sustained outage self-fences through the lease keepalive instead. A consecutive-failure budget (`ROUTER_RECONCILE_FAILURE_BUDGET`, default 12 ticks; same default on pods) bounds the partial mode where snapshot reads fail while the lease stays healthy, and `personhog_coordination_reconcile_failures_total{component}` counts every failure.
- **Warm provenance**: A pod records what each partition warm was installed for (serving, or a specific handoff id). Warming honors only a warm installed for the *current* handoff — one left over from an earlier ownership era is released and rebuilt, because its cache can hold values that predate writes the changelog accepted since, and a fresh warm replays only from the writer's committed offset. Without this, a returning owner whose `Released` convergence never ran could ack a warm it never performed and lose acknowledged writes — a counterexample the stateright model found and now pins.
- **Coordinator restart**: On startup, the coordinator runs `reconcile_pending_handoffs`. For every existing handoff it applies cleanup if `Complete`, otherwise calls `check_phase_advance` to nudge the state machine. This handles the case where acks were written before the coordinator was up — the ack-watch only fires on Put events, so without reconcile those acks would be invisible.
- **Reconcile tick**: Beyond the startup reconcile, the coordinator re-evaluates every in-flight handoff on a fixed interval (`reconcile_interval`, default 5 s). This is the liveness backstop for state changes that fire no watched event — e.g. a router departing (nothing watches router registrations) newly satisfying a freeze quorum. Everything the tick drives is idempotent: phase transitions use CAS and cleanup tolerates already-deleted records.
- **Lease loss (self-fencing)**: Connection trouble and lease loss are different things. A broken or silent keepalive stream is a fact about one connection — the lease lives in etcd's replicated keyspace and stays valid until its TTL passes without renewal — so ambiguous keepalive failures rebuild the stream and retry (a fresh connection through the service reaches a healthy member) for as long as the last confirmed renewal is recent; a routine single-member restart costs some retries (`personhog_coordination_keepalive_retries_total{component}`), not a fence. The keepalive declares loss on exactly two signals: etcd answering a round with TTL ≤ 0 (authoritative — the lease is revoked or expired), or the renewal margin running out (two thirds of the TTL without a confirmed renewal — the final third is reserved so the fence completes before the coordinator can possibly treat the lease as expired; retrying past it would gamble split-brain against availability). On loss the component ends the coordination attempt immediately, skipping the graceful drain: the coordinator already considers it dead and is reassigning its partitions via the dead-owner path, so a graceful drain would only race that. A pod self-fences *locally* before anything else: every held partition is drained and, once quiesced, released (dropping its cache and serving authority — re-acquisition always re-warms). A partition whose drain cannot quiesce is deliberately **not** released — release is what unfences admissions and drops the cache, and a leaseless pod must do neither over live in-flight work — so it stays fenced and held, in-place recovery is refused, and the process restart clears it by death. A zombie owner therefore never keeps serving partitions the protocol has reassigned beyond the window that restart closes. Lease loss is observed at every await the session makes while holding a lease — the attempt select, the backoff nap between failed attempts, and the graceful drain all race the keepalive — so once the keepalive declares loss, the fence is never deferred by supervisor state. Every other session end fences too — budget exhaustion and shutdown revoke the lease, which deletes the registration instantly, so the local fence runs first (a no-op after a completed graceful drain) and the dead-owner path never meets a still-serving owner. On lease loss the fence's drain budget is the runway the keepalive margin reserved (a third of the TTL), not the full graceful drain timeout; overshoot poisons recovery and the process restart clears stragglers by death.
- **Supervised coordination runs (etcd resilience)**: A failed coordination attempt — a broken watch stream, a failed etcd write, an exhausted reconcile budget — no longer kills the process; the run supervisors tear the attempt down cleanly, back off exponentially, and rebuild through the same bootstrap that recovers a restarted process, while the data plane keeps serving. The two participant classes recover *differently*, on purpose. A **router** sheds its registration on every failed attempt (its registration is a freeze-quorum vote, and a registered but non-acking router would stall every quorum until the phase deadline); serving through its gap is safe because handoffs created while it is unregistered exclude it from their quorums and the leader-side fences reject its stale forwards. A **pod** does the opposite: its lease session (grant, register, heartbeat) lives *above* the attempt loop and survives attempt failures, so the coordinator keeps seeing a live pod and never runs the dead-owner path against a process that is still serving — the invariant is that serving authority is held exactly as long as the lease-backed registration behind it. This matters because the dead-owner path has no fence: its safety rests entirely on a deregistered owner being unable to produce, so a pod must never voluntarily deregister while it still serves. Only lease loss ends a pod session, self-fencing locally (every held partition released; re-acquisition re-warms) before a fresh session registers anew. A consecutive-failure budget (`ROUTER_RUN_RETRY_BUDGET`, default 10; same default on pods) keeps a genuinely wedged participant on the process-restart path; an attempt that made real progress — a convergence applied, a reconcile pass completed — resets the count, and the reset is keyed on measured progress rather than elapsed time because a time threshold silently exempts every failure detector slower than it (the reconcile budget and the stall watchdog both take a minute to fire), and `personhog_coordination_run_restarts_total{component}` counts every rebuild.

### Concurrency and atomicity

- All phase advancement uses `cas_handoff_phase`, a CAS on the handoff key's `mod_revision`. Two watchers racing to advance the same handoff cannot both succeed; the loser observes `false` and leaves the work to the Put event from the winner. (`mod_revision` rather than per-key `version`: `version` resets to 1 when a key is deleted and recreated, so a stale guard could match a different incarnation of the handoff.)
- Every snapshot read that seeds a watch is revision-anchored: the read returns the etcd revision it was served at, and the watch starts at `revision + 1`. An event landing between the snapshot and the watch attaching is replayed rather than lost. When two snapshot reads feed one watch (e.g. a pod's startup reconcile reads assignments and handoffs), the watch anchors to the *lower* of the two revisions so nothing between them is skipped.
- Advancing to `Complete` uses an atomic etcd transaction that writes both `phase=Complete` and the new `PartitionAssignment` together. Routers can never observe a torn state where the phase has advanced but the assignment hasn't (or vice versa).
- Routing changes flow through handoff `Complete` events; there is no separate assignment watch. An out-of-band write to `assignments/{partition}` is not invisible, though — the reconcile pass converges the table against the assignment keys every tick, so it flips routing within seconds, with no freeze, no drain, and no fence in front of it. That is exactly why nothing may mutate those keys outside the handoff protocol.

## Known limitations

**The double-zombie residual — status by half.** A lease-expired router (excluded from the freeze quorum, still routing on a stale table) feeding a lease-expired pod (coordination loop dead, never fenced) can ack a write after the partition's new owner warmed; the write lands beyond the warm HWM, invisible to the new owner forever. Both zombie windows are bounded by lease self-fencing to roughly one heartbeat tick, so the loss needs both to coincide — but nothing rejects the zombie's produce at the broker. The stateright model reproduces the exact interleaving (`current_protocol_double_zombie_loses_acked_writes`) and machine-validates the fix (`Variant::EpochFenced`). Where each piece stands, one bullet per residual:

- **Zombie writes: closed behind `KAFKA_TRANSACTIONAL_FENCING` (default off).** A partition's owner acquires its transactional id before the warm read, so a predecessor that missed its drain is fenced at the broker and its produce fails instead of landing. Changelog consumers read `read_committed`, so aborted windows are never visible. The guarantee binds per binary, not per flag flip: a pod still running the old build produces non-transactionally and no epoch can fence it, so enable the flag only once the whole fleet is on a build that carries it — which the default-off flag and enable-after-rollout ordering already encode.
- **Zombie reads: closed behind `LEASE_GATED_AUTHORITY` (default off).** The keepalive publishes its last confirmed renewal and the request path refuses once that stamp is older than the renewal margin — checked at admission and again before answering, since the claim can lapse while a read is served. A stalled keepalive therefore fences implicitly. The model confirms fencing and the gate are complementary rather than alternative: each alone leaves stale reads; only together does every safety property hold.
  - *Residual, recorded because the model's `serve_read` points here:* the closure is only as prompt as the claim's lapse. Natural expiry always lapses the stamp before etcd deletes anything, but an out-of-band *revocation* removes the registration while the stamp is still fresh, and only the deliberately best-effort registration watch converts that into an immediate surrender. With the watch dead, the stamp stays valid for up to one heartbeat (`prompt_detection_is_what_makes_the_read_gate_hold` pins exactly this). No production path revokes another pod's lease, so reaching the window takes an operator.
- **Acquisition is gated on the same claim.** A zombie waking inside its lease window would otherwise re-acquire the partition's transactional id on its way to noticing it is dead, fencing the legitimate owner — the broker grants the epoch to whoever initializes last. Warming and resume consult the authority stamp before acquiring and again after, dropping the fence rather than building on a claim they no longer hold. The e2e zombie gate manufactures the waking-zombie shape and asserts by consequence; the per-arm rejection coverage lives in the deterministic fencing integration tests. Because the two mechanisms only work together, `KAFKA_TRANSACTIONAL_FENCING` is refused at startup without `LEASE_GATED_AUTHORITY`.
- **A condemned producer heals in place.** An abort that did not land, or a commit whose outcome stayed unknown, leaves a producer no later window can be begun from. It is condemned and given up on the next write, which answers as unowned (`FailedPrecondition`, the router's bounce class) rather than as a retryable failure, and the serving-side verification re-acquires on the next convergence tick — gated on the authority stamp, which is what gives a pod the standing to bump the epoch.
- **The drain commits its own window when it can.** A request cancelled mid-produce takes its handler — and the drain's in-flight count — with it, leaving the record it enqueued in a window nobody waits on; the drain waits (bounded, best-effort, never failing the drain) for that window to commit before acking, landing the cancelled write below the successor's cutoff. The successor's `init_transactions` aborts whatever could not settle — safe in either ordering, because the transaction coordinator serializes the in-flight commit against the successor's init on the shared transactional id.
- **Writer progress is coupled to leader transaction liveness.** `read_committed` means the writer cannot advance past an open window: a leader that stops mid-window holds every `read_committed` consumer of that partition at the last stable offset until the broker abandons the transaction — bounded by the derived broker transaction timeout (about 6s at the production lease). The price of aborted windows never reaching Postgres.

**Rollout placement residuals** (`k8s_awareness_enabled`, default off). During a Deployment rollout the coordinator holds old-generation Ready pods and caps incoming pods at their final share, keyed on departing-generation registrations rather than the transient k8s rollout flag. Placement-behavior residuals, none affecting write safety (the handoff protocol is unchanged):

- **Some partitions move twice.** Orphans that overflow onto Hold members when no capped pod has room move again when capacity appears, and ceil-rounded caps can leave the final balance one leveling move away. The cost of every partition always having an owner.
- **Intent loss degrades to policy-free planning.** A Deployment deleted mid-rollout, a watcher stream dying between evaluations (stale intent until the lazy rewatch reports), or the k8s API being down all fall back to plain balanced placement — availability over placement. A freshly elected coordinator bound-waits (`FIRST_INTENT_WAIT`) for its first intent per controller, so failover mid-rollout does not plan policy-free unless the API server is actually unreachable.
- **A capped pod's in-flight steal counts against its cap before it lands.** Planning attributes pinned handoffs to their targets, so a capped member briefly under-fills while its steal is in flight; the next evaluation after completion levels it.
- **With `KAFKA_TRANSACTIONAL_FENCING` off there is no settle equivalent.** Nothing forces a queued record to the broker before the drain acks, so it can land above the new owner's warm cutoff, and a later write for that person re-derives the same version — where the writer's first-wins guard keeps the record nobody acked and discards the one that was. The unfenced path is slated for removal once fencing proves out.

**Assignment strategies are minimal**: The two bundled strategies (`JumpHashStrategy` and `StickyBalancedStrategy`) are basic implementations meant to exercise the coordination layer. `JumpHashStrategy` is stateless and deterministic but ignores current assignments entirely, causing unnecessary partition movement on every rebalance. `StickyBalancedStrategy` minimizes movement but uses a naive greedy approach without considering locality, rack awareness, or weighted pods. Both are placeholders to be replaced with a production-grade strategy as requirements become clearer.

**A late plan chunk can install an owner that just deregistered.** Chunked replacement units (successors, reaffirms) are guarded on their records, not on pod liveness, so a unit applied after its plan's snapshot can complete toward a pod that died in between — routers cut over and fail closed until the next replan moves the partition; nothing is acked and lost. The window predates chunking (plan-to-apply was already seconds wide) and grows with plan size under it. The stateright `chunked_plans` mode covers chunked creations; extending it to replacement units is open.

**Mid-stream watch reconnects don't replay missed events — bounded by reconciliation**: The snapshot-to-watch-attach gap is closed (watches are revision-anchored to the snapshot that seeded them), but if an *established* etcd watch stream drops and the underlying client reconnects, events that fired during the disconnect are not replayed. Every participant now bounds the resulting staleness with its level-triggered truth path — the coordinator's tick (which also wakes the planner unconditionally), the router's reconcile pass, and the pod's converge-all tick — so a missed event costs at most one reconcile interval, not correctness.
